# F0 / F1 恢复水位合同与实施记录

日期：2026-11-11。基线为 sha-7890b5c，工作分支 codex/recovery-watermarks-f1。

## 本批行为

- 成员投递状态查询、确认回执和补偿记录的必需读写失败，会抛出 DeliveryStateError。成员推送入口结束该成员本轮处理，并保留最后一条状态已保存消息的水位。
- 查询失败与“没有已发送记录”分别表达。数据库状态不可读时，不继续调用该消息的外部发送。
- 部分路由的成功记录在补偿记录写失败前已独立提交时，恢复后仍跳过已确认的路由。
- 博客文章逐篇事务落库。每团水位只跨过按旧到新顺序连续存在于数据库的文章。
- 解析或落库失败的文章保留为水位缺口，其他文章和团体仍可归档。后续读取同一列表时，仅处理缺失文章。
- 处理中 URL 的预留由实际处理任务持有，在成功、异常或取消后的 finally 中释放。尚未结束的取消清理继续持有预留。
- 水位查询失败向上报告。首次启动防刷屏和水位超出列表窗口时的原有策略由独立回归验证。

本批沿用现有表和路由标识，没有写入新的暂挂状态。兼容的旧调用仍返回原业务类型，必需状态失败现在显式报错。

## 验证

新增 tests/test_recovery_watermarks.py，14 项用例覆盖补偿 INSERT 失败、回执 INSERT 失败、状态不可读、三个失败文章位置、取消、部分提交、其他任务持有预留、跨团体隔离、数据库重新打开和首次启动策略。

原代码的初始 8 项回归中 6 项失败。修复后 14 项通过，相关采集、取消、博客、路由测试共 85 项通过。Ruff、编译和差异检查通过。

测试数据库和媒体目录使用临时目录。新回归的第一次失败运行发现旧路径会调用后台 sent_id 写入，已将测试的 SENT_IDS_DIR 设置到临时目录。后续验证均采用该隔离设置。

## F2 的状态合同和发布前置条件

下一批区分待发送、发送中、确认送达、确认失败、送达未确认、状态待修复、归档待补齐和配置暂停。外部送达状态与业务完成状态分别保存。

外部请求与 SQLite 无法组成同一个事务。F2 需要在提交请求前保存可恢复的发送意图，发送成功后保存回执。发送意图或回执无法可靠保存时，暂停该路由并向管理员暴露待核实对象。

新暂挂状态启用前，必须证明所有发送入口及回滚版本都能识别它。发布兼容读取能力后，才能写入新状态，并以该兼容版本作为回滚下限。

## 尚待后续批次解决

- 外部实际已发出、但成功回执写入失败的情形，还需要 F2 的发送意图与暂挂机制来避免再次发送。本批只停止后续消息并保留水位。
- 博客已归档但在推送前被取消，仍需 F2 的持久投递待办恢复通知。
- 失败文章离开源站有限列表窗口后，仍受原有水位脱节策略影响。跨窗口恢复需要持久待办或单独选择的历史补档策略。
- 报告中的 A3–A11 仍按 remediation-plan.md 执行。

因此本批是 A1/A2 已复现水位与取消缺陷的修复，不代表发送持久化、博客投递和全部历史缺失已经验收。

## 发布和回滚

通过 PR CI 后，本批可独立发布。部署使用固定 SHA 镜像，核对健康、实际版本、首轮消息/博客状态和错误日志。现有配置及数据表可由发布前版本读取。

回滚到已验证的发布前镜像，保留最新成功回执、待补偿记录和归档内容。水位恢复为旧版本行为会重新暴露本批缺陷，应保留故障记录并安排修复前进。
