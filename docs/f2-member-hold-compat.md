# F2 成员投递暂挂兼容读取合同

日期：2026-11-16。范围：F2 的先行兼容版本，不启用新暂挂/发送意图写入。

## 为什么先发布这一批

当前 pending/suspended 之外的状态会被旧 reconcile 重新置为 pending；只在新版本写 held 并不能防止回滚后自动重发。因此先发布保留受保护状态、所有内部成员发送入口都遵守阻塞的读取版本，再实现持久发送意图及结果写入。

本批不将现有 timeout/delivery_failed 批量转换为暂挂，不清空历史队列，也不产生新的 held/in_flight 行。正常 pending/suspended 的恢复行为保留。

## 状态和入口合同

- pending、suspended 是旧有可自动转换状态；除此之外的状态（held、in_flight、未来未知状态及无法识别的空值）保守保护。
- 受保护行对应的整个“团体×成员×路由” lane 暂停发送，避免后续消息越过它；其他健康路由继续。
- 自动配置同步不得将受保护状态恢复为 pending；普通补偿写入不得覆盖受保护记录及其阻塞信息；旧成功记账入口不能替代显式核实来清除受保护 lane。
- notifier.send_member_message_detailed 在发送与官方媒体预处理前核对保护状态。被保护路由产生明确 delivery_held 结果；缺少成员 ID 或读取状态失败时明确失败，不进行外部发送。
- 内部正规成员调用携带 group_type/m_id。旧布尔接口保留，但缺少 group_type 时以同 member_id 跨团保守查询保护路由，不能借缺失团体字段绕过。只有暂挂路由时不得把空 attempts 误当成成功。
- skip_route_ids 仍表示已有成功或本轮已阻塞目标，不用于解除保护。匹配路由集合保持可见，避免“没有尝试”被解释成“没有匹配”。

入口盘点：message_worker -> fetcher.push_member_messages -> _handle_message -> notifier.send_member_message_detailed；本地待补偿通过同一 fetcher 流程回放。兼容 notifier.send_member_message 委托同一详细入口。Web 消息回填委托 tools/backfill_archive.py 归档，不调用成员推送接口；社媒和博客是独立业务路由，本批不改变其状态语义。

## 验收

隔离 SQLite 手动植入受保护状态（仅测试），验证同路由重启后不发送、关闭/重新启用路由不解除保护、普通补偿/成功记账不清除保护、健康目标继续、旧布尔接口不能误报成功。覆盖数据库不可用/查询失败及成员身份不全，不调用真实外部通道。

上线前后只读核对现有 route_state 分布、配置与凭据指纹、实际镜像版本、QQ 在线状态和巡查结果。首批发布不迁移 schema，不运行生产故障注入，不重复全量媒体备份。

## 后续写入批次必须另行通过的门禁

1. 发送前原子保存意图、提交阶段与拆批结果；状态保存失败禁止请求。
2. 发送后超时、取消和进程退出持久暂挂；明确尚未提交时安全重试。
3. 管理员“确认已送达/显式重发”的权限、审计、并发领取和尝试标识。
4. 各发送入口的并发保护及回滚演练；将本兼容版本设为最低允许回滚版本后，才能启用新状态写入。旧版 sha-99e29fd 不能在新暂挂写入启用后作为直接回滚目标。
5. 可见的暂挂统计、任务定位及恢复入口。

本批不解决博客逐段回执与持久投递待办、社媒状态/归档补偿，也不宣称 F2 或 A3–A5 完成。

## 本批验证记录

- 隔离加载原始 99e29fd 代码可复现：reconcile 将 held 转成 suspended 再恢复 pending；普通补偿将 held 覆盖为 pending 并增加尝试次数；旧成功记账允许向受保护 lane 写入新成功事实。
- 新增 13 项回归覆盖持久保护、重启、配置关闭/启用、未知状态、缺失/空白团体、数据库读取/初始化失败、旧布尔接口、健康路由继续与非发送计数。
- 独立审查未发现阻塞问题；查询到发送之间的并发竞争、发送后回执丢失与持久意图仍属于下一批写入门禁，不在本兼容版本启用。
