# 生产化与安全加固落地计划

## 1. 目标与范围

本计划将项目从“可稳定运行的个人生产服务”提升为具备可重复发布、可回滚、最小网络暴露、可审计和可观测能力的服务。实施完成后，外部访问统一使用 `https://zakapush.220206.xyz`，业务容器及 frp 隧道端口不再直接向局域网或公网暴露。

本计划覆盖以下系统：

- 群晖 NAS 上的 Docker 容器、frpc 与持久化目录；
- GCP 上的 frps、Lucky 反向代理、防火墙和 TLS；
- GitHub Actions、GHCR 镜像和仓库内的部署工具；
- Web 管理端认证、审计、测试与运行监控。

不在本计划中：业务规则重写、推送渠道扩展、历史数据迁移或更换云厂商。

## 2. 目标网络拓扑

```text
浏览器
  |
  | HTTPS :443
  v
zakapush.220206.xyz -> GCP Lucky
                         |
                         | 127.0.0.1:46046
                         v
                       frps
                         |
                         | 经认证的 frp 隧道
                         v
                       群晖 frpc
                         |
                         | 127.0.0.1:46046
                         v
               sakamichi-push Docker 容器
```

边界要求：

- 群晖容器仅绑定 `127.0.0.1:46046`；
- frpc 只连接群晖本机的 `127.0.0.1:46046`；
- GCP 的 frps 代理端口仅绑定 `127.0.0.1`；
- GCP 公网仅接受 Lucky 的 HTTPS 流量（以及受源地址限制的 frp 控制端口）；
- 所有用户访问均经由域名和 Lucky，避免绕过 TLS、限流与访问日志。

## 3. 实施原则

1. 先轮换已暴露或曾硬编码的凭据，再修改部署方式。
2. 配置、密钥、数据和应用镜像必须分离；部署不得覆盖 `config/config.json`、`data/` 和 `logs/`。
3. 每项线上变更都必须包含可验证的健康检查与明确回滚方法。
4. 生产环境只部署可追溯的镜像摘要或 Git SHA，不使用不确定的 `latest` 作为发布依据。
5. 网络收口应在域名链路验证成功后再切换，避免锁死运维入口。

## 4. 里程碑与任务

### M0：准备与凭据处置（第 0–1 天）

**目标：** 建立安全的变更前状态，消除硬编码凭据风险。

| 任务 | 具体操作 | 验收标准 |

| 补充仓库保护 | 配置 `.gitignore`，启用 GitHub secret scanning，并在 CI 运行凭据扫描。 | 含疑似密钥的提交被阻断或告警。 |

**实施前确认项：** 部署脚本中的历史凭据是否已在其他地方使用；GCP 防火墙规则和 Lucky 配置的实际保存路径；frpc 是宿主机服务还是 Docker 容器。

### M1：网络收口与管理端加固（第 1–3 天）

**目标：** 让 HTTPS 域名成为唯一的用户入口，同时保留 frp 隧道连通性。

#### 4.1 群晖侧

1. 将 `docker-compose.yml` 和 `docker-compose.with-napcat.yml` 的端口发布保持为：

   ```yaml
   ports:
     - "127.0.0.1:46046:46046"
   ```

2. 在 frpc 的对应 TCP 代理中使用：

   ```toml
   [[proxies]]
   name = "zakapush-web"
   type = "tcp"
   localIP = "127.0.0.1"
   localPort = 46046
   remotePort = 46046
   ```

3. 若 frpc 运行在 Docker 容器中，`127.0.0.1` 指向 frpc 自身而非 NAS 宿主机；应改用 host network 或明确的宿主机网关后再执行切换。
4. 设置生产环境变量：

   ```dotenv
   WEB_ADMIN_ORIGIN=https://zakapush.220206.xyz
   AUTH_COOKIE_SECURE=true
   WEB_ADMIN_TOKEN=<仅存于受限密钥存储中的随机值>
   ```

#### 4.2 GCP 侧

1. Lucky 为 `zakapush.220206.xyz` 配置 TLS 证书，并将上游固定为 `http://127.0.0.1:46046`。
2. 强制 HTTP 跳转 HTTPS，启用 HSTS；保留反向代理访问日志，不记录认证头或 Cookie。
3. frps 设置代理监听地址为 `127.0.0.1`（`proxyBindAddr`），避免 `remotePort=46046` 被公网直接访问。
4. 防火墙仅开放：
   - `443/tcp`：公网；
   - frp 控制端口：仅群晖的固定出口 IP 或可信 VPN 网段；
   - 运维 SSH：仅管理员固定 IP / VPN。
5. frp 开启强认证和 TLS；使用专用 token 或 OIDC，不复用应用管理员令牌。

#### 4.3 验收与回滚

切换顺序：先验证 Lucky 可访问 GCP `127.0.0.1:46046`，再更新群晖 frpc，最后重新创建群晖容器应用端口限制。

验收命令与预期：

```bash
# 应返回成功状态，并最终跳转至 /archive
curl -I https://zakapush.220206.xyz/

# 应返回 200
curl -fsS https://zakapush.220206.xyz/api/health/status

# 从非 GCP、非 NAS 的第三方网络测试，应连接失败
curl --connect-timeout 5 http://<GCP 公网 IP>:46046
curl --connect-timeout 5 http://<NAS 局域网 IP>:46046
```

若域名不可用：先恢复容器原端口绑定或暂时撤销 GCP 的代理端口监听限制，确认 frpc 日志后再重试；不要通过长期重新开放 46046 来替代修复。

### M2：版本化发布与自动回滚（第 3–7 天）

**目标：** 用不可变镜像替代 `docker cp + restart` 的在线文件覆盖。

项目已具备 GitHub Actions CI 与 GHCR 多架构镜像发布。此阶段将其接入实际生产流程。

| 任务 | 具体操作 | 验收标准 |
| --- | --- | --- |
| 镜像标识 | CI 为每次构建输出 Git SHA 标签和镜像 digest；发布记录保存二者。 | 任一运行版本可对应到唯一提交。 |
| Compose 参数化 | 使用 `IMAGE_REF=ghcr.io/...@sha256:...` 注入生产 Compose，而不是只引用 `latest`。 | `docker compose config` 显示固定 digest。 |
| 部署脚本重写 | 执行 `pull`、保存上一 digest、`docker compose up -d`、等待健康检查；不再执行 `docker cp`。 | 发布不会修改运行中容器文件。 |
| 自动回滚 | 健康检查或外部 HTTPS 烟雾测试失败时，自动恢复上一 digest。 | 人为注入失败版本可自动恢复。 |
| 配置隔离 | 仅挂载生产 `config/`、`data/`、`logs/` 与受控 `.env`；镜像内代码不可被持久卷覆盖。 | 重建容器后配置和数据保留、代码版本正确。 |

建议的部署步骤：

```text
选择已通过 CI 的镜像 digest
  -> 备份当前 digest 和配置校验和
  -> docker compose pull
  -> docker compose up -d
  -> 等待容器 health=healthy
  -> 请求 HTTPS 健康接口与关键页面
  -> 成功：记录发布；失败：恢复上一 digest 并告警
```

### M3：质量门禁与供应链安全（第 2 周）

**目标：** 让已存在的 CI 从“执行检查”升级为“阻止不合格版本发布”。

1. 设置 `pytest --cov` 最低覆盖率阈值，并按核心模块分别统计认证、归档、推送和配置加载覆盖率。
2. 保留现有 Ruff 与全量测试；在 PR 上强制要求它们通过。
3. 增加依赖漏洞扫描（例如 `pip-audit`）与 Python 静态安全扫描（例如 Bandit）。
4. 对镜像生成 SBOM，并在高危基础镜像或依赖漏洞出现时阻止发布。
5. 增加容器集成测试：启动临时 Compose、验证认证 Cookie、跨 Origin 拦截、归档写入和 `/api/health/status`。
6. 对发布镜像进行签名，并在 NAS 部署前校验签名或 digest 白名单。

验收标准：含高危依赖漏洞、密钥泄露、静态检查失败、核心测试失败或覆盖率低于阈值的提交无法发布生产镜像。

### M4：可观测性、审计与恢复（第 2–3 周）

**目标：** 发生故障时能发现、定位、恢复，并回答“谁在何时做了什么”。

| 领域 | 落地项 | 成功标准 |
| --- | --- | --- |
| 日志 | JSON/结构化日志、请求 ID、任务 ID；认证头、Cookie、令牌全部脱敏。 | 可按一次推送或一次管理员操作检索全链路日志。 |
| 指标 | 容器重启、frpc 连通、队列积压、推送成功率、HTTP 延迟、认证失败数。 | 仪表盘能显示 24 小时趋势。 |
| 告警 | 容器 unhealthy、frpc 断链、连续推送失败、磁盘空间不足、认证失败激增。 | 通过演练可在规定时间内收到告警。 |
| 审计 | 记录管理员标签修改、认证失败、权限不足和关键配置变更。 | 审计记录可关联用户、时间、来源和操作结果。 |
| 备份恢复 | 定期备份 `config`/`data`；每季度在隔离位置执行恢复演练。 | 恢复演练达到既定 RPO/RTO。 |

### M5：持续代码治理（持续进行）

1. 将过宽的 `except Exception` 按网络、解析、认证、磁盘和第三方 API 错误分类处理。
2. 统一外部 API 响应模型与输入校验，减少字典式隐式约定。

5. 每季度审查依赖、管理员账号、网络规则和恢复演练结果。
