# 2026-10-12 Message 巡查持续失败：代理隧道连接泄漏

## 证据与结论

NAS 镜像 `sha-0d4f73c` 使用 HTTPX 0.28.1 / httpcore 1.0.9，经
`192.168.22.2:7890` 的 HTTP CONNECT 代理访问 Message API。

- 16:42:50 最近一次正常巡查：11 个参与成员请求成功。
- 16:45:47–16:46:02 多个独立 API 出现空 `ConnectError`，随后转为 `PoolTimeout`。
- 此后连续多个小时请求成功 0、异常 11、正常跳过 2。单成员 60 秒预算包含
  信号量排队，导致连接池等待进一步放大为整轮成员超时。
- 调查时在同一容器中，新建客户端通过原代理和直连均能立即获取 API 根路径
  的 HTTP 404；旧进程持续超时。这排除了“调查时外网一直不可达”的解释。

在 NAS 原始 Python 环境中，用本机临时代理返回 CONNECT 200 后关闭 TLS 握手，
池上限设为 2，复现结果：

| 客户端 | 连续 4 次注入故障 | 代理恢复后同一客户端访问真实 HTTPS API |
| --- | --- | --- |
| 原版 | ConnectError、ConnectError、PoolTimeout、PoolTimeout | PoolTimeout |
| 修复版 | 4 次 ConnectError | HTTP 404（成功建连并收到 API 响应） |

原版复现池状态显示 **0 个活跃请求、0 个排队请求、2 个 ACTIVE 连接、0 个 IDLE
连接**。CONNECT 200 后 TLS 失败没有将底层连接标为 CLOSED，连接池永远不能
回收这些名额。20 个连接的生产池会在累计相同故障后完全失去请求能力。
上游问题及待合并修复：

- https://github.com/encode/httpcore/discussions/921
- https://github.com/encode/httpcore/pull/1049
- https://github.com/encode/httpcore/pull/1056

历史日志仅记录两层空 ConnectError，无法还原 16:45 那次 TLS/代理故障的具体
断开原因。可以确定的持续停摆机制是上述依赖缺陷，加上本项目仅在整轮 900 秒
超时/传输关闭时重建池；成员 60 秒超时使轮次正常以 error 结束，不触发恢复。
共享池和信号量排队放大影响，但无需人为扩大池容量或增加重试来解决泄漏。

## 修复

`src/proxy_transport.py` 为本项目的 HTTP(S) 代理 transport 创建专属 tunnel
子类：未建立隧道时出现错误或取消，在传播原异常前关闭该连接。连接池正常
回收失败连接，其他活跃请求不受重建/关闭整个池的影响。

通用、认证、博客的长期客户端工厂及主程序博客客户端统一使用该适配器。
直连/SOCKS 路径不受该修复影响。保留证书校验、代理认证、连接限额、请求超时，
不自动重放 GET/POST，也不调整认证逻辑、并发及订阅数据。

日志格式增加最多 6 层异常原因（含被上游隐藏的 context），仍统一脱敏，
使后续 TLS EOF、DNS 或系统连接错误可以从日志辨认。

依赖范围约束为 HTTPX 0.27–0.28、httpcore 1.0.x（至少 1.0.9）。本适配器使用
httpcore 内部接口，升级时必须运行真实代理测试；上游发布完整修复后应评估
移除适配器，避免长期维护内部接口。

## 验证

- Windows 本地相关回归 74 项通过，覆盖认证、取消、池生命周期、巡查结果和启动。
- 新测试真实模拟 TLS EOF、TLS 超时、握手取消、代理认证、其他并发请求不中断，
  以及真正容量竞争仍正常抛出 PoolTimeout。
- NAS 同容器 A/B 故障注入通过；恢复验证经实际代理访问真实 Message HTTPS API。
- 上述 API 404 只证明请求通道恢复，真实账号巡查结果需要部署后单独核验。

## 部署后的观察标准

恢复真实巡查成功后，至少观察 3 轮的请求成功数、PoolTimeout 和耗时。保留旧镜像
与环境文件备份，出现启动失败时回滚。存活探针只判断调度进程存活，不能用
`healthy` 代替真实巡查成功；验收以成员请求统计和投递记录为准。
