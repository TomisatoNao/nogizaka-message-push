# 坂道归档前端设计规范

> 版本：1.0 · 适用范围：`src/webui_static/` 及后续所有 WebUI 页面
>
> 这是一份持续有效的设计约束，不是一次性的改版方案。新增页面、组件或视觉调整前，agent 必须先阅读本文件；如果实现需要偏离规范，应在变更说明中写明原因、影响范围和回滚方式。

## 1. 产品定位

本项目的前端是“坂道内容归档与运维工作台”，不是官方站点的复刻，也不是营销落地页。设计应优先服务于：

1. 长时间浏览消息、博客和媒体归档；
2. 快速筛选、定位和对比内容；
3. 管理监控账号、推送通道和运行状态；
4. 在桌面、平板和手机上保持稳定、可读、可操作。

视觉关键词：**克制、柔和、清晰、耐看、内容优先**。任何装饰都不能降低信息密度、对比度或滚动稳定性。

## 2. 核心原则

### 2.1 统一基础，局部表达

- 全局背景、文字、边框、控件、状态和阴影使用共享 token。
- 页面可以有不同密度：管理端偏紧凑，归档端偏内容和媒体；但不能各自发明一套颜色、圆角和交互语义。
- 三坂颜色只表达来源或内容上下文，不把整个页面染成某一坂的主题。

### 2.2 内容优先

- 先保证标题、正文、时间、来源、状态和操作可读，再考虑装饰。
- 不使用会持续跳动、漂移或遮挡内容的背景动画。
- 无限滚动、长文本和大图场景必须保持布局稳定，不能因为装饰元素或媒体加载导致内容跳动。

### 2.3 渐进披露

- 首屏只展示完成当前任务所需的信息。
- 高级配置、诊断信息和专家 JSON 放入明确标识的折叠区或弹窗。
- 说明文字优先一句核心说明，详细内容再通过展开、帮助文本或链接提供。

### 2.4 可预测的交互

- 相同语义的按钮、输入框、状态徽章和弹窗必须有相同的视觉和行为。
- 加载、成功、警告、失败和未配置状态必须有明确反馈，不能只依赖颜色或控制台日志。
- 任何异步操作都要处理重复点击、失败回包、取消和过期响应。

## 3. 主题与视觉 token

共享 token 位于 [`src/webui_static/theme.css`](../src/webui_static/theme.css)。新样式优先复用 token，不得在页面中重新定义同名语义。

### 3.1 表面层级

| 层级 | 用途 | 规则 |
| --- | --- | --- |
| `--bg` | 页面背景 | 只承载内容，不作为控件背景 |
| `--card` / `--card-solid` | 卡片、模块、弹窗 | 主要内容容器使用这一层 |
| `--card-soft` | 控制组、说明块、次级分组 | 不承担主要文字对比 |
| `--field` | 输入框、选择框 | 输入状态和禁用状态必须可区分 |
| `--border` / `--border-soft` | 边界和分隔线 | 优先细边框，不使用强黑线 |

透明度、渐变和 `backdrop-filter` 只能增强层级，不能让文字与背景混在一起。深色主题必须单独检查边框和灰阶对比度。

### 3.2 强调色与语义色

- `--accent`：通用操作、当前选中、焦点和主要动作，当前为克制的中性紫。
- `--brand-nogizaka`：乃木坂语境紫。
- `--brand-hinata`：日向坂语境蓝。
- `--brand-sakurazaka`：樱坂语境白/银灰；浅色主题中不得直接使用近白文字作为唯一信息。
- `--ok`、`--warn`、`--err`：成功、警告、失败，只用于状态，不用于装饰。

规则：

1. 全局导航、保存、搜索等普通操作使用 `--accent`，不要因为当前页面内容属于某一坂就改变全部控件颜色。
2. 来源标签、成员筛选、内容徽章可以使用对应品牌色，但必须同时满足文字对比度。
3. 状态不能只通过颜色区分，至少还要有文字、图标或可访问名称。
4. 新增颜色先判断是否属于 token；临时颜色必须写出用途，并在后续整理进 token。

### 3.3 形状、间距与阴影

当前基础形状：

- 大模块/弹窗：`--radius`（约 15px）；
- 小分组/控件：`--radius-sm`（约 9px）；
- 胶囊标签：`border-radius: 999px`；
- 细节按钮可以使用 6–8px，但同一组件族必须一致。

推荐间距阶梯：`4 / 8 / 12 / 16 / 24 / 32px`。新增布局尽量使用阶梯值，避免出现大量相近的 10、14、18、20px。

阴影只表达层级：普通卡片使用 `--shadow-sm`，浮层/弹窗使用 `--shadow-md` 或 `--shadow-lg`。不要通过大面积阴影制造装饰感。

### 3.4 字体与信息层级

- 复用 `--font` 和 `--mono`，不要为单个页面引入另一套字体。
- 页面标题 > 模块标题 > 正文 > 元数据/说明，至少保持两个层级的字号或字重差异。
- 时间、来源、计数和辅助说明使用 `--muted`，但不得低于可读对比度。
- 代码、账号 ID、端口和环境变量名使用等宽字体或明确的代码样式。

## 4. 组件规范

### 4.1 页面框架

- 顶部导航统一使用 `.app-header` 和共享导航组件。
- 页面内容使用明确的最大宽度和左右内边距，不能每个页面自行设定一套容器宽度。
- 管理端模块优先使用 `.admin-module`、`.admin-module-heading`、`.admin-control-group`、`.admin-data-group`、`.admin-actions` 和 `.admin-note`。
- 归档页可以使用时间线、媒体卡片和侧栏，但颜色、边框、圆角和状态仍来自共享 token。

### 4.2 按钮

按钮分为三种语义：

1. 主要动作：保存、提交、确认，使用 `.btn.primary` 或对应组件的 primary 变体；
2. 普通动作：搜索、刷新、打开设置，使用中性按钮；
3. 危险动作：删除、清空、撤销，使用错误状态色，并需要确认或明确撤销路径。

按钮必须：

- 有明确文字或 `aria-label`；
- 有 hover、active、focus-visible、disabled 状态；
- 手机端触控区域不低于 44px；
- 不通过颜色 alone 表示成功或失败；
- 异步提交期间防止重复提交并保留失败重试入口。

### 4.3 输入框与选择器

- 使用统一的背景、边框、圆角、焦点环和错误状态。
- 标签、占位符和帮助文本不能互相替代；重要字段必须有可见标签。
- 输入错误显示在具体字段附近，并在提交失败时聚焦第一个错误。
- 路径、备注、端口和数量等字段要有前端快速校验，但后端校验仍是最终防线。
- 不把密钥、Cookie 或 Token 写入 DOM、localStorage、URL、raw JSON 或日志。

### 4.4 标签、徽章与状态

- 徽章用于短状态或计数，不承载长说明。
- 状态徽章统一使用成功/警告/失败/中性语义类。
- 长错误原因放到说明文本、详情区或 `title`，避免把表格撑宽。
- 选中态必须同时体现背景/边框/文字，不能只依赖一个细色条。

### 4.5 弹窗与浮层

- 弹窗必须有标题、关闭按钮、焦点进入和关闭后的焦点回归。
- Esc、取消、右上角关闭按钮应保持一致语义。
- 内容区域滚动，标题和底部操作栏保持稳定；手机端不得超出视口。
- 背景遮罩只能用于聚焦，不得造成过度模糊或影响阅读。

### 4.6 表格与长列表

- 桌面端保持列对齐，移动端只允许表格容器横向滚动。
- 禁止页面整体产生横向滚动。
- 长列表和无限滚动必须采用稳定的占位尺寸，媒体加载不能让已读位置跳动。
- 空状态、加载状态和失败状态都要有明确的内容，而不是空白区域。

### 4.7 归档媒体与灯箱

- 媒体是内容主体，不叠加无关装饰边框或动画。
- 灯箱中的关闭、下载和“前往消息/博客”操作应保持固定位置。
- 从灯箱跳转到消息或博客默认打开新标签页，保留原浏览上下文。
- 背景点击只能关闭灯箱，不得误触发底层图片或上一张/下一张操作。

## 5. 响应式与滚动规则

| 断点 | 布局原则 |
| --- | --- |
| `>900px` | 侧栏、摘要、操作栏优先横向排列；桌面侧栏可 sticky |
| `641–900px` | 控件允许换行，摘要和控制组切换为两列或可换行 Flex |
| `≤640px` | 单列布局；模块标题、状态和操作按顺序堆叠；触控区至少 44px |

滚动规则：

- 顶部导航桌面高度约 60px；sticky 内容应保留可见的呼吸间距，目前侧栏使用约 76px 顶部偏移。
- 移动端优先使用普通流布局，除非 sticky 能明显改善操作且经过真实设备验证。
- 任何 sticky 元素都必须验证：不会被导航遮挡、不会遮住正文、不会在无限滚动时产生跳动。
- 视觉装饰不得绑定每个列表项生成；相册、时间线和瀑布流应保持稳定的背景与层级。

## 6. 动效与性能

- 默认使用现有 `--tr`/`--tr-fast`，动效以 150–250ms 的状态反馈为主。
- 不使用持续循环动画、滚动绑定大面积重绘或随机装饰。
- 尊重 `prefers-reduced-motion: reduce`，至少关闭位移、脉冲和自动播放效果。
- 图片优先使用缩略图、懒加载和稳定的宽高比；大图、视频和灯箱不得阻塞首屏。
- 静态资源行为变更必须递增查询版本，避免 immutable 缓存继续使用旧文件。

## 7. HTML、CSS 与 JavaScript 约束

1. `theme.css` 保存跨页面 token 和共享组件；页面 CSS 只保存页面特有布局。
2. 不新增布局型内联 `style`。动态数值使用 class、`data-*` 或受控 CSS 变量。
3. 不使用未经说明的 `!important`；确需覆盖时注明原因和作用域。
4. 不删除或重命名已有 ID、数据属性、API 路径和配置字段来解决视觉问题。
5. 前端异步请求必须处理过期回包、取消、失败提示和重试，不得只在控制台报错。
6. HTML 结束标签、脚本加载顺序和静态资源版本保持唯一、可检查。
7. 页面专用样式与共享样式冲突时，优先修正 token 或组件变体，不通过越来越高的选择器优先级堆叠覆盖。

## 8. Agent 实施流程

### 修改前

- 阅读本规范和相关页面现有 CSS/HTML；
- 明确这是 token、共享组件、页面布局还是单点 bug；
- 先确认是否涉及配置结构、API、数据或权限，纯视觉任务不得顺手改变这些边界；
- 记录目标视口、主题、交互状态和回滚点。

### 修改中

- 优先复用已有 token 和组件类；
- 保留现有 ID、事件入口和数据序列化语义；
- 一次只改变一个视觉维度，避免颜色、布局、动画同时大幅变化；
- 对桌面、平板、手机和浅色/深色主题分别检查。

### 修改后

- 运行相关前端契约测试和视觉回归；
- 至少执行 `ruff check .`、`python -m compileall -q src tests`、对应的 `node --check` 和 `git diff --check`；
- 说明缓存版本、视觉基线和浏览器兼容影响；
- 若要提交、推送或部署，单独记录提交号、镜像标签和健康检查结果。

## 9. 审查清单

- [ ] 是否复用了共享 token，而不是新增相近的硬编码颜色？
- [ ] 浅色和深色主题文字、边框、选中态是否都清晰？
- [ ] 三坂品牌色是否只出现在来源语境，没有污染全局操作？
- [ ] 是否存在新增布局型内联样式、无说明的 `!important` 或重复组件？
- [ ] 桌面、平板、手机是否无页面横向溢出？
- [ ] sticky、灯箱、无限滚动是否经过真实交互验证？
- [ ] 键盘焦点、Esc、错误提示和 reduced-motion 是否可用？
- [ ] 静态资源版本、契约测试和视觉基线是否同步？
